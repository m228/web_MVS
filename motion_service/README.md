# Сервис движения — анализ видео с IP-камер по зонам → Modbus

Отдельный процесс рядом с `web_MVS` (как `cv_service` и `video_service`). Камера (RTSP или видеофайл) → зоны-полигоны →
по каждой зоне «движется / нет» → биты, уровни и наработка в регистры/coils контроллера по Modbus TCP.
Применения: **датчик вращения ленты** (там, где нет датчика), **уровень жома в шахте** (3 окна → 0..3), **жом на ленте** (зоны + наработка в %).

Всё настраивается в браузере на странице **«Движение»** web_MVS (кнопка на главной): камера, зоны (обвёл мышью по живой картинке),
пороги с графиком, группы зон, адреса в ПЛК, проверка связи. Отдельных программ разметки не нужно.

## Установка (один раз)

1. Python 3.10+ в PATH. Через `update.bat` (меню «Что обновить?») Python 3.12 ставится сам, если его нет; вручную нужен только при запуске `setup.bat` напрямую.
2. **`setup.bat`** — создаст `.venv` и поставит зависимости (OpenCV, NumPy, FastAPI, pymodbus). GPU не нужен.
   Системный прокси подхватит сам.

На машине с релизным web_MVS (без git) — **`UpdaterMotion.bat`** в папке web_MVS: скачает `motion_service_v*.zip` из последнего
релиза в `motion_service\` и при первом запуске сам вызовет `setup.bat`. Настройки (`data\`) и `.venv` обновление не трогает.
GitHub не отдаёт файл — скачать архив на другом компе и `UpdaterMotion.bat -ZipPath "D:\motion_service_v….zip"`.

## Запуск

Руками не нужно: web_MVS сам поднимает сервис при старте (без окна, вывод — в `motion_service\service.log`) и раз в минуту
проверяет `/health`; упал — поднимает снова. Адрес `127.0.0.1:8768`. Отключить автозапуск: `plate_config.json` →
`"services": {"motion": {"autostart": false}}`, тогда — `run.bat`. Без web_MVS сервис тоже работает (`run.bat`), но настраивать
его тогда можно только через API (`PUT /config`).

Адрес сервиса меняется в `plate_config.json` → `"motion": {"service_url": "http://127.0.0.1:8768"}`.

## Как это работает

По каждой зоне считаются **две метрики** за кадр (показываются в панели «КЗ», решает выбранная в поле `metric`):

| Метрика | Что это | Когда брать |
|---|---|---|
| `diff` | средняя разность текущего и предыдущего кадра внутри зоны (уровни серого) с вычитанием общей смены яркости — мерцание ламп и автоэкспозиция не считаются движением | датчик вращения: лента с рисунком/швами/материалом |
| `flow` | оптический поток Farneback — устойчив к мерцанию и сжатию видео; так работают шахта и лента жома | ровный жом, слабое движение, плохая картинка |

Дальше: сглаживание (`smooth` кадров) → гистерезис `on` / `off` + debounce (`frames_to_on` / `frames_to_off`) → бит зоны.
Зона `motion` активна при ВЫСОКОЙ метрике (движется), `presence` — при НИЗКОЙ (густой ровный жом гасит поток).

**Калибровка порога:** вкладка «Тренды» нижней панели «КЗ» в мультипросмотре: график метрики зоны с пунктиром on/off и полоской «крутится / стоит / нет данных». Запусти ленту, останови — по разрыву между
«стоит» и «крутится» поставь `on` чуть ниже «крутится», `off` чуть выше «стоит». «● запись CSV» пишет `flow`/`diff` каждого кадра
в базу `data\motion.db`; «⤓ архив» отдаёт их CSV — можно разобрать в Excel.

**Запись всех камер и сводка сбоев.** В общем виде панели «КЗ» (кнопка «все камеры») «● все» включает запись метрик сразу по всем камерам с КЗ
(правка настроек камеры запись не рвёт — продолжается новым запуском), «⤓ архив» скачивает всё одним zip: CSV по запускам записи (собираются из базы) и
`summary.txt` — по каждой камере сколько времени была в норме и список сбоев (когда, на сколько, почему: картинка застыла, битый поток, нет кадров,
пропуск без единой строки) плюс события связи (поток оборвался / источник открыт). В CSV у каждой строки колонки `alive` и `status`.
Такой архив можно отдать на разбор: сразу видно, все ли ленты работали и когда какая пропадала. Размера файла больше не ограничиваем — запись идёт в базу.

**База `data\motion.db` (SQLite, с 2.1.7).** Всё, что сервис пишет на диск, лежит в одном файле: тренды, записи метрик по кадрам и сводка снимков (CSV остался
только выгрузкой по кнопке «⤓ архив»). Компактно: имена камер и зон — числами, время — целым, значения — целыми ×10000, на 3 зоны одной камеры около 6–7 МБ
в сутки против 14 МБ у прежних CSV. Запись идёт пачками раз в 5 с. **Хранение:** сырое (секундные точки и кадры записи) — 60 суток; корзины статистики
по 10 с (среднее / мин / макс) и сводка снимков — навсегда, это в разы меньше. **Тренды на диске:** графики и «среднее / мин / макс» не обнуляются после
обновления: сервис при старте читает базу обратно.

**Снимки «в один момент».** Раз в 20 минут по часам (:00, :20, :40) все включённые камеры снимаются одновременно:
`data\shots\<день>\<ЧЧММСС>\<камера>.jpg` + `log.json` (связь, статус, значения зон) (JPEG хранятся 10 суток), а сводка по зонам — в таблице `shot` базы (навсегда).
На кадре нарисованы зоны (зелёная — «движется», красная — «стоит») и текущие diff / flow: можно сравнить картинку с графиком, например как зоны
отработали ночью. Мёртвая камера в `log.json` есть, без картинки. Снять прямо сейчас: `POST /shots/now`.

**Автозапись и срок хранения.** На первом запуске (нет `data\recording.json`) запись по всем камерам включается сама; выключили вручную —
после перезапуска не пишется. Сырое старше 60 суток и JPEG снимков старше 10 суток удаляются сами. Свободного места меньше 1 ГБ — сырое режется до 7 суток,
снимки не делаются (в журнале предупреждение). Настройки в окружении сервиса: `MOTION_AUTORECORD=0` (не включать запись сама), `MOTION_SHOTS_MIN=0` (не снимать),
`MOTION_SHOTS_MIN=N` (шаг, мин), `MOTION_KEEP_DAYS=N` (срок сырого, суток), `MOTION_SHOTS_KEEP_DAYS=N` (срок JPEG снимков).

**Запись переживает перезапуск сервиса.** Что включено («● все» или «●» у камеры), запоминается в `data\recording.json`: после обновления или сбоя сервис сам
продолжает запись, в новом файле. Выключили вручную — после перезапуска не пишется. Буфер уходит на диск не реже чем раз в 5 с (хвост при остановке — не больше).
В `summary.txt` перерыв между файлами одной камеры виден отдельным списком («Перерывы между файлами записи»).

**Значения зон: сейчас / среднее / мин / макс.** В карточке каждой зоны (панель «КЗ») под названием — `diff` и `flow`: текущее значение и среднее, минимум,
максимум за выбранный период (5 мин … 24 ч, по умолчанию 3 ч; выбор над списком зон). Считаются только по кадрам в норме (застывшие, битые и «каша» не идут),
значения сглажены так же, как на графиках. Копятся в самом сервисе (корзины по 10 с, сутки), поэтому после его перезапуска начинаются с нуля — карточка пишет
«накоплено за …». Чтобы настроить порог: запусти ленту в нужном режиме на час-другой и возьми ср / мин / макс — `on` чуть ниже «крутится», `off` чуть выше «стоит».
Для долгой истории и передачи на разбор — запись CSV: в `summary.txt` архива по каждой зоне те же среднее / мин / макс и доля времени «крутится».

**Зона `cycle` и группа `mirror` — углы двух палок на валах (диффузия).** На каждом валу тонкая палка: красная половина в одну сторону от оси,
синяя в другую. Зона `cycle` задаётся не полигоном, а центром оси `center` [x, y] и радиусом `radius` (в пикселях кадра разметки) и считает угол
красного конца от вертикали по часовой, 0..360°. Ищется только по цвету: для каждого угла φ берётся доля красных точек на луче φ плюс доля синих на
луче φ+180, лучший φ и есть угол (фон по медиане не годится — колёса за палкой тоже вращаются). Считаются только тонкие цветные полоски (`thin` — ширина «окна открытия» в пикселях, 9; 0 — не
отсекать): сплошные цветные области (кожух, тени) палкой не считаются. Синего в цехе много, поэтому он подспорье с весом `blue_w` (0,5): палка принимается при
красном на луче не меньше `red_min` (0,12) либо при синей тонкой полосе почти на всю длину (`blue_alone`, 0,6). Найденную палку дальше ищут около ожидаемого угла
(прошлый + скорость вращения × время, окно `jump_deg` = 25°, при пропаже растёт на 1°/с), поэтому одиночные ложные пики её не уводят. Палку не видно (переход
по тёмному или зелёному, блик) — до `coast_s` секунд (30; 0 — не держать) сервис держит ожидаемый угол и скорость (`coast: true`, `bit` = 0, на кадре пунктир),
а не прыгает на ближайшую кромку; дольше — палка потеряна и ищется по всему кругу. Частота кадров на это почти не влияет: валы делают < 1 об/мин, 1–4 кадра в секунду дают
одинаковый результат; важно, чтобы палка была видна. Цвета — `red_hsv`
[H≤, H≥, S, V] и `blue_hsv` [H от, H до, S, V] (оттенок по шкале OpenCV 0..179; по умолчанию красный [16, 165, 50, 55] — мягче прежнего [12, 163, 70, 80], потому что красный конец в сумерках бледнеет и желтеет; зоны, сохранённые с прежним значением, переходят на новое, свои значения не трогаются), поиск принимается при уверенности `min_score` / `min_conf`.
В истории, трендах и CSV у такой зоны `flow` = угол (°), `diff` = уверенность, `bit` = «палка найдена».
«Крутится / стоит» — поле `moving` в состоянии зоны: за `stop_s` секунд (10) угол сдвинулся меньше `stop_deg` (5°) — стоит, больше 1,6·`stop_deg` — крутится, между — как было; `null` — пока неизвестно (мало данных или палка потеряна). Вал идёт ~4,7°/с, поэтому остановка видна за ~10 с. Стоит — обороты сразу 0. Если палки не видно, а парная в кадре, «крутится / стоит» берётся у парной (валы зеркальны), а при остановке ожидаемый угол не двигается. Приложение (журнал камер, отчёт смены) считает по `moving` события «вал крутится / стоит» с началом и длительностью, а не по `bit`.
Группа `mirror` берёт две cycle-зоны: `mode` `mirror` (по умолчанию: палки зеркальны, θ1 + θ2 = 360°) или `same` (θ1 = θ2); `ref` — поправка
эталона в градусах; `delta` = отклонение от нормы (−180..180°); бит аварии включается при |delta| ≥ `tol` (по умолчанию 10°, выключается ниже 0,7·tol,
debounce `frames_to_on` / `frames_to_off`). Не видно хоть одной палки или нет кадров — delta не считается, авария 0. Пока хоть одна палка в удержании (`hold: true` в состоянии группы — угол достроен по скорости), delta показывается, но аварию ни включаем, ни гасим: достроенный угол врёт на градусы.
В ПЛК: зона-цикл в `holding` — угол в 0,1° (0..3599), в `coil` — «найдена»; группа mirror в `holding` — delta в 0,1° знаковым int16 (−5,0° → 65486),
в `bits`/`coils` — бит аварии.
**Обороты вала.** Зона `cycle` считает и обороты: наклон непрерывного (без скачков через 360°) угла по точкам последних `rpm_window` секунд (20 по умолчанию),
об/мин, «+» по часовой, «−» против; пока данных мало или палка потеряна — 0. В состоянии это поле `rpm`; в ПЛК — `rpm_out` зоны (`holding`): обороты в 0,01 об/мин знаковым int16
(−0,73 об/мин → 65463). Когда вал стоит (`moving: false`), `rpm` и регистр сразу 0. В интерфейсе скорость — в карточке вала («0,79 об/мин ↻» или «стоит ■»), регистр задаётся строкой «скорость в ПЛК» в карточке зоны.
**Поправка по углу (`table`).** Камера стоит сбоку и объектив искажает, поэтому даже ровные валы дают delta, которая зависит от положения палки
(на реальной камере за оборот от −7° до +10°, воспроизводится от дня ко дню). Группа может нести таблицу из 36 чисел (ячейки по 10° по углу первой палки,
линейная интерполяция по кругу): `delta = θ1 ± θ2 − table(θ1) − ref`. Снимается кнопкой «снять за оборот» в карточке синхронности
(`POST /cameras/{id}/mirror_table {"group": …}` — по покадровой истории последних ~5 минут: нужны ≥ 60 кадров и ≥ 28 ячеек из 36, то есть валы ровные
и палки прошли полный оборот; разброс таблицы больше 60° — отказ). Таблица запоминает текущее положение как норму, после сдвига камеры снимать заново;
`ref` остаётся ручной добавкой поверх неё («текущее = норма» подгоняет её под текущую delta).
**Самоподстройка поправки (`learn`, `learn_min`).** По умолчанию включена (`learn: true`, окно `learn_min` = 30 мин, 5..240). Сервис сам выучивает волну Δ
за оборот: в каждую из 36 ячеек по углу первой палки кладёт остаток по кадрам (обе палки найдены, не в удержании, вал крутится, отклонение от ожидаемого
не больше 60°), берёт медиану за скользящее окно и вычитает среднее по ячейкам. Выученная **форма** добавляется к ручной таблице; **постоянный сдвиг и
медленный дрейф в неё не попадают**, остаются в Δ и дают тревогу. Размах формы ограничен ±25°, форма подходит к новой плавно (раз в 10 с, на четверть пути),
первая считается после ≥ 28 заполненных ячеек по ≥ 3 кадра. Форма хранится в `data\mirror_learn_<камера>.json` (раз в минуту, если менялась) и переживает
перезапуск и смену настроек; сменили ручную таблицу — прежняя форма отбрасывается. В состоянии группы: `learn` {`ready`, `bins`, `amp`, `window_min`}
и `shape` (36 чисел) — по ним интерфейс вычитает форму на графике Δ. На ночной записи завода (03→04.11, 115 тыс. кадров): разброс Δ p5…p95 −3,7…+10,2° → +2,3…+4,5°;
при допуске 5° и эталоне по уровню кадров с тревогой 57,6 % → 0,17 %, включений 3008 → 21 за 16 часов.

**Вид окна: жом есть / пусто / движется.** По движению «шахта пустая и стоит» и «жом есть, но стоит» неотличимы — метрика в обоих случаях ниже порога. Поле зоны `fill_metric` (в панели — «вид окна»): `rel` — яркость окна относительно металла вокруг него (яркость в зоне / медиана полосы вокруг окна: свет, солнце и автоэкспозиция почти не влияют; по роликам шахты жом ≈ 0.9, пустое окно ≈ 0.65 — рекомендуется), `lum` — средняя яркость в зоне, `tex` — зернистость (средняя |кадр − размытый кадр|; на роликах разделяет слабо); `off` — не считать (по умолчанию). Значения сглажены за `fill_smooth` кадров, видны в карточке зоны и пишутся в CSV записи колонками `<зона>_tex`, `<зона>_lum`, `<зона>_rel`, `<зона>_fill` (только у зон с включённым видом окна), на снимках — `t=`, `L=` и `r=`. Пока `fill_on` = 0, пороги не заданы и признак только измеряется: решения нет. Заданы `fill_on` / `fill_off` (on — верхний порог, off — нижний, как у движения) — по ним (`fill_frames` кадров подряд) решается «жом есть»; `fill_invert` — жом при НИЗКОМ значении. Состояние окна `state`: **0 — пусто и стоит, 1 — жом есть и стоит, 2 — движется** (движение главнее). Вывод зоны в ПЛК (`out.value`): `bit` — бит движения (как раньше) или `state` — состояние окна; пока пороги не заданы, при `state` пишется бит. Пороги подбирают по записи: включить запись, снять пустую шахту, шахту с жомом и наполнение, по `_tex` / `_lum` найти разрыв между «пусто» и «жом».

**Уровень жидкости (декантатор): зона `level` и группа `level`.** Два мерных стекла на одной камере; уровень берётся не из движения, а из маски жидкости,
которую даёт YOLO-модель в отдельном сервисе (`level_service/`, порт 8770; модель грузится из браузера на вкладке **«Уровень»** панели «КЗ»).
Зоны-стёкла (`type: "level"`, обычный полигон) рисует человек: «Разметить стёкла» — сначала нижнее (рабочее), потом верхнее (его может не быть).
Группа `type: "level"` (1–2 зоны, нижняя первой) раз в `infer_interval_s` (2 с) отправляет свежий кадр сервису уровня и считает **по каждому ответу модели**
(как в LVLDec.exe, `LevelProcessor` в `motion_level.py`):

1. уровень стекла = площадь(маска жидкости ∩ зона) / площадь(зона), 0..1; жидкости в кадре нет совсем — берётся прошлое значение (память);
2. отсечка осадка: ниже `glass1_min` / `glass2_min` (%, по умолчанию 15 / 20) считаем стекло пустым;
3. калибровка полного: `glass1_full` / `glass2_full` (%, 100 — выкл.) — сырой уровень, который модель даёт при ПОЛНОМ стекле, растягивается до 100 %;
3а. (нет в LVLDec) верхнее стекло считается, только когда нижнее заполнено не меньше `glass2_gate` (%, 90 — по базе завода 07–12.11 при жидкости в верхнем нижнее ≥ 90 у 98,8 % точек; 0 — как в LVLDec): на дне верхнего стекла
   корка осадка, модель видит её на 10–25 %, и её дрожь у порога `glass2_min` бросала нижнее в 100 % (пики на тренде, 12.11.2026: сотни раз за сутки);
4. жидкость в верхнем стекле ⇒ нижнее заведомо полное; гистерезис у потолка: выше 96 % — 100 %, сброс ниже 96 %;
5. сглаживание EMA (`alpha`, 0,93); первые `warmup_s` (10) секунд после старта камеры — без сглаживания;
6. **Total = (нижнее + верхнее) · 50 %**: каждое стекло 0..50 %, вместе 0..100 %. `value` группы = Total ×10 (0..1000: 54,3 % → 543, SCADA делит на 10).

Модель молчит дольше `hold_s` (30 с), нет кадров или камера мертва — `valid: false` и нули (в сценарий, как у других КЗ, уходит 0). Причина видна в панели.
Параметры модели: `conf` (0,35), `imgsz` (0 — как при обучении), `liquid_class` (`liquid` — имя класса жидкости; для другой модели — другое имя),
`geometry` (`lvldec` — маска растянута вместе с полями letterbox, как в LVLDec.exe, цифры совпадают с заводскими; `exact` — без растяжения), `contour` — отдавать контур
жидкости в состоянии (рисуется на плитке тонкой линией). У зоны `flow` = уровень стекла 0..100 %, `diff` = сырой уровень до отсечки и сглаживания — оба идут в тренды и CSV.
В состоянии группы: `total`, `g1`, `g2` (0..50), `raw`, `conf`, `ms`, `model`, `err`, `age_s`, `valid`, `warmup`.
**Как у валов — три места в интерфейсе.** Кнопка «Разметить стёкла» в шапке панели «КЗ» (рядом с «Разметить валы»; то же есть на вкладке «Уровень»). На плитке камеры в каждом стекле —
«палка» уровня: белая линия на измеренной высоте и заливка под ней, они двигаются вместе с жидкостью; справа от стекла стрелка и заполнение в %, сверху по центру Total и вклад стёкол.
На вкладке «Зоны · тренды» — карточка «Уровень»: Total сейчас, по каждому стеклу сейчас / среднее / мин / макс за выбранный период, строка про модель и запись в ПЛК, справа график
(Total и заполнение нижнего и верхнего стекла; окно времени общее с остальными графиками, колесо мыши). График строится из тех же рядов зон (`flow` = заполнение стекла), отдельного API не нужно.
**Клик по графику — кадр на этот момент.** Раз в `shots_every_s` (60 с; 0 — выкл.) поток модели кладёт маленький JPEG того же кадра (640 px, качество 70, ≈ 40 КБ)
в `data\level_shots\<камера>\<группа>\<unix-секунды>.jpg`; старше 2 ч (самое длинное окно графика) стираются. `GET /cameras/{id}/level_shot?group=&ts=` отдаёт
ближайший снимок (не дальше 1,5 периода, минимум 90 с; время — в `X-Shot-Ts`). В окне снимка — время, уровни с графика и стрелки «раньше / позже».

**Запись в ПЛК — как у всех КЗ, через сценарий.** Вкладка «Уровень» заводит сценарий `lvl_<камера>` («Уровень · камера», правило «сумма», источник — группа) **со своей связью
с ПЛК, выключенной по умолчанию** (`modbus.enable: false`): пока на заводе LVLDec.exe пишет в тот же регистр, второй писатель не нужен. Тумблер, IP, порт, Unit ID и регистр —
там же. Включить без IP нельзя.

**Перенос настроек LVLDec.** «Импорт config.ini LVLDec…» на вкладке (или `POST /level/import {"ini": текст}`) берёт из его `data\config.ini` зоны `[zones]`
(пиксели кадра 1920×1080), пороги, прогрев, интервал, `glass*_full` и ПЛК (IP, порт, Unit ID, регистр), кладёт их в группу и сценарий. Не переносятся heartbeat-счётчик,
перезапуск по залипанию и плановый перезапуск, сжатие кадра: их роль у сторожа кадра и сервиса. Модель (`26x_detection.pt`) загружается отдельно.

**Картинка для SCADA и браузера (`webview` у камеры) — перенос блока `[webview]` из LVLDec.** Это не видеопоток: на каждый запрос отдаётся один готовый JPEG, страницы сами
перезагружают его по таймеру. Кадр готовится не по запросу, а раз в `update_sec`, поэтому сколько бы ни было зрителей, нагрузка одна. Настройка — карточка «Картинка для SCADA»
на вкладке «Уровень» (квадратик в шапке включает). Ключи те же, что в `config.ini` LVLDec: `enabled` (по умолчанию выкл.), `host` (`0.0.0.0` — вся сеть, пароля нет — только LAN),
`port` (5000, у каждой камеры свой), `update_sec` (5), `jpeg_quality` (85), `annotate` (выкл.), `crop_x1 crop_y1 crop_x2 crop_y2` (пиксели ОРИГИНАЛЬНОГО кадра, все 0 — без обрезки;
иначе x2 > x1 и y2 > y1), `output_w` и `output_h` (размер после обрезки, обе 0 — не менять). Картинка: обрезка → размер (`INTER_AREA` при уменьшении, иначе линейно) → метка времени
снизу слева → JPEG.

| Адрес | Что отдаёт |
|---|---|
| `/scada.jpg` | **адрес для SCADA** (её скрипт ходит на него): кадр с разметкой, если `annotate` включён, иначе обычный кадр, как `/frame.jpg`; до первого — 503 |
| `/frame.jpg` | последний обычный кадр (всегда без разметки); до первого — 503 «нет кадра — камера ещё не готова» |
| `/scada.html`, `/scada.htm` | минимальная страница для SCADA: картинка на весь экран, обновление по таймеру и `meta refresh` |
| `/`, `/index.html` | страница для человека с переключателем «Сырой / С разметкой» |
| `/frame_annotated.jpg` | кадр с разметкой — только при `annotate`; иначе 503 «аннотированный кадр ещё не готов» |
| `/healthz` | `{"ok":true,"raw_age_sec":…,"annotated_age_sec":…,"annotate":…}` — возраст картинок для мониторинга (-1 — ещё не было) |

Разметка (`annotate`): как у отладчика LVLDec — полупрозрачная маска жидкости, рамка с подписью «liquid 0.96» и сверху две строки `Total=… g1(low)=… g2(up)=…` и статус слоёв.
Строки рисуются на полном кадре до обрезки, поэтому обрезка слева-сверху их срежет (как и в LVLDec). Камера молчит дольше 5 с — картинка не обновляется (остаётся последняя, на ней своя
метка времени, `raw_age_sec` растёт). **Порт занят** (старый LVLDec.exe ещё работает): в состоянии камеры `webview.error` и строка в журнале, повторы через 0,5, 2, 5, 15 с и дальше каждые 30 с; как только порт
освободится, сервис займёт его сам (первая неудача после правки настроек не считается: прежний сервер ещё закрывает порт). Занять чужой порт «поверх» нельзя (на Windows `SO_REUSEADDR` это позволил бы). Правка настроек пересоздаёт камеру, как любая другая правка.

**Группы** складывают зоны: `sum` — сколько активно; `monotonic` — уровень снизу вверх (верхнее окно активно → нижние засчитаны,
шахта); `worktimer` — наработка за окно `window_s` в % (`scale` 100 → 0..100; 4095 — для аналогового выхода).

**Битый поток («серая каша»).** При потере пакетов декодер H.264 заливает кадр ровным серым ~128. Сервис считает долю таких блоков
(`corrupt_ratio`, по умолчанию 0.3; 0 — не проверять): пока кадры битые и ещё `corrupt_hold_s` (2 с) после них, результаты НЕ учитываются —
биты и записи в ПЛК держат последнее значение, на кадре зоны серые. Если каша длится дольше `freeze_timeout_s` — камера считается мёртвой
(нули, status = 0). На графике такие моменты — серый фон.

**Нагрузка на процессор.** Основное съедают две вещи, у каждой своя настройка (панель «КЗ» → параметры камеры и зоны):
- **Декодирование видео.** Камера отдаёт все кадры (обычно 25 к/с, 4 Мп), а анализируется 1–3 в секунду: декодировать приходится каждый, пропустить нельзя.
  Поле камеры `hw_accel` (в панели — «Декодирование»): `auto` (по умолчанию) / `d3d11` — видеоядро (Intel UHD и т.п., через Direct3D 11), `off` — процессор. Камеры, у которых в `motion_config.json` уже записано `"hw_accel": "off"`, остаются на процессоре, пока не выбрать другое в панели.
  Не открылось с видеоядром или три раза подряд не дало ни одного кадра — сервис сам возвращается на процессор до своего перезапуска (в `service.log` строка «дальше декодирую процессором»).
  В панели у живой камеры после «к/с» стоит **GPU**, если поток реально идёт через видеоядро. Нужен OpenCV с FFmpeg ≥ 4.5.2 (из `requirements.txt` ставится такой).
- **Оптический поток (`flow`).** Считается для каждой зоны на каждом кадре, даже когда зона решает по `diff`, и на крупной зоне это больше половины процессора.
  Поле зоны `track_flow` (галочка «flow» у зоны): выключите для зон на `diff` — flow считаться не будет, а в графиках, записях CSV и сводке его значение будет 0.
  Зона на `flow` считает его всегда. По умолчанию включено, как раньше.
- **Дополнительный поток.** Поле камеры `substream` (в панели — «Поток»): вместо основного потока Dahua (`subtype=0`) берётся дополнительный (`subtype=1`) —
  картинка меньше, декодер нагружается слабее. Адрес без `subtype=` не меняется. Значения `diff` и `flow` зависят от разрешения: после смены пороги снимите заново.

**Сценарии записи в ПЛК** (`scenarios` в конфиге, вкладка «ПЛК · сценарии»): берут зоны любых камер, считают правило — `or` (хоть одна
крутится), `and` (все), `sum` (сколько) — и пишут одно значение в `holding` или `coil` через общий канал ПЛК. Мёртвая камера даёт 0.
Источники удалённых камер/зон из сценария отбрасываются при проверке конфига.

## Вывод в ПЛК (Modbus TCP, holding-регистры и coils)

| Что | Куда |
|---|---|
| бит зоны (`out`) | `holding` — регистр 0/1, `coil` — бит |
| группа `out.kind = holding` | значение группы (сумма, уровень, % наработки) в один регистр |
| группа `out.kind = bits` | биты зон группы в один регистр (бит 0 = первая зона) |
| группа `out.kind = coils` | coil на каждую зону: адрес, адрес+1, … |
| `status_out` камеры | 1 — камера жива, 0 — нет кадров / картинка застыла |

**Камера пропала или картинка застыла** дольше `freeze_timeout_s` → все биты и уровни = 0, `status` = 0; когда кадры вернулись —
детектор оживает сам. Обрыв потока КОРОЧЕ `freeze_timeout_s` (по умолчанию 10 с) состояния зон не сбрасывает: после переподключения
биты держатся как были (сбрасывается только буфер кадров), поэтому ложного «стоит» на каждом коротком обрыве нет; настоящая остановка
при дырах в потоке замечается с задержкой до `freeze_timeout_s`. Запись идёт отдельным потоком: при каждом изменении и ещё раз каждые `write_period_s`; недоступный ПЛК
не тормозит детекцию. «Проверка связи» (вкладка «ПЛК · сценарии») читает ОДИН регистр — в ПЛК ничего не пишется.

## Конфиг

`data\motion_config.json` (создаётся при первом сохранении из интерфейса, 20 последних копий — `data\backups\`). Координаты зон — в пикселях
кадра, на котором размечали (`frame_size`); если камера отдаёт другое разрешение — пересчитываются сами.

## Эндпоинты

| | |
|---|---|
| `GET /health` | жив, версия, камер / из них живых |
| `GET /config`, `PUT /config` | весь конфиг; плохой → 400 с текстом по-русски, ничего не применяется; перезапускаются только изменённые камеры |
| `GET /state` | состояние камер: биты зон, `flow`/`diff`, группы, ПЛК |
| `GET /cameras/{id}/snapshot?w=1100` | последний кадр JPEG; размер оригинала — заголовки `X-Frame-W/H` |
| `GET /cameras/{id}/level_shot?group=lvl&ts=…` | снимок для графика уровня, ближайший к моменту (хранятся 2 ч); его время — `X-Shot-Ts` |
| `GET /cameras/{id}/history?n=300` | ряды для графиков |
| `GET /cameras/{id}/stats?window=10800` | среднее / мин / макс `flow` и `diff` по зонам за window секунд (до суток), только кадры в норме; `groups` — по группам синхронности: Δ уже С коррекцией и сама поправка (ср / мин / макс), по каждому кадру с видимыми палками без удержания; копится в памяти (после перезапуска сервиса начинается заново) |
| `GET /cameras/{id}/visibility?window=86400` | видимость палок (зоны `cycle`): доля времени «найдена» окнами за window секунд (до 7 суток, из секундных трендов на диске); `t` — начала окон, `zones` — % по окнам или `null` (мало данных / камера молчала), `avg` — по всему периоду. Секунда = «найдена хотя бы в одном кадре секунды», поэтому цифры на несколько процентов выше долей по кадрам |
| `POST /shots/now` | снять все камеры «в один момент» → `data\shots\…` |
| `POST /cameras/{id}/record` | `{"on": true}` — писать метрики кадров в базу |
| `POST /modbus/ping` | прочитать один регистр |
| `POST /level/import` | `{"ini": текст config.ini LVLDec}` → зоны, пороги, ПЛК для камеры (ничего не сохраняет) |
| `GET /logs` | последние строки журнала |

## Проверка без камеры

В «Адрес потока» можно указать путь к видеофайлу — он крутится по кругу в темпе своего FPS. Тесты: `.venv\Scripts\python.exe -m pytest tests\test_motion_service.py`
в корне репозитория (ядро, Modbus, поток камеры, сервер целиком).
